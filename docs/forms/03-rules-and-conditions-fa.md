# ۰۳ — شرط‌ها و منطق شرطی

این سند پاسخِ «چطور فیلدها را به هم وصل کنیم — گزینه‌های فیلد بعدی تغییر کند،
یا بر اساس مقداری که در فیلد قبلی انتخاب شده مجموعه فیلدهای کاملاً متفاوتی
نمایش داده شود» است.

شرط یک **درخت JSON** است، نه یک رشته. نه `eval` وجود دارد، نه پارسر عبارتی که
باید امن شود، و نه سطح حملهٔ تزریق. فرم‌ساز هر شرط را به‌صورت جمله‌ای فارسی به
نویسنده بازمی‌گرداند، تا پیش از انتشار، اشتباه در شرط دیده شود.

مرجع: `shared/form-engine/src/rules.ts`، ارزیابی‌شده توسط `evalRule`.

## ساختار

```ts
type Rule =
  | { op: "always" }
  | { op: "and"; rules: Rule[] }
  | { op: "or";  rules: Rule[] }
  | { op: "not"; rule: Rule }
  | { op: "eq" | "ne" | "in" | "nin" | "contains"
        | "gt" | "gte" | "lt" | "lte"
        | "exists" | "empty" | "filled";
      path: string; value?: unknown }
  | { op: "anyIn" | "everyIn" | "someTrue" | "someFalse";
      path: string; value?: unknown }
  | { op: "count"; path: string; gte?: number; lte?: number };
```

## نشانی‌دهی مسیر

`path` درخت پاسخ را نشان می‌دهد. بخش‌ها:

| بخش | معنا |
| ---- | ----- |
| `key` | خواندن آن ویژگی |
| `key[]` | پیمایش همهٔ عناصر آرایه |
| `key[2]` | خواندن یک عنصر با اندیس |

`[]` تودرتو می‌شود و همین باعث می‌شود شرط بتواند به درون گروه‌های تکرارشونده
برسد:

```
severity
vehicles[].type
vehicles[].driver.health
vehicles[].passengers[].health
pedestrians[].health
```

درون یک گروه تکرارشونده، شرط‌ها **برای هر ردیف جداگانه** ارزیابی می‌شوند: شرطی
روی `mobility` فقط mobility همان وسیله را می‌خواند، نه همهٔ وسایل را.

## مرجع عملگرها

### ساختاری

| عملگر | معنا | نکته |
| ----- | ----- | ----- |
| `always` | همیشه درست | شکل رایج برای «الزامی» |
| `and` | همهٔ فرزندان درست | `and` خالی **درست** است |
| `or` | هر فرزند درست | `or` خالی **نادرست** است |
| `not` | نفیِ فرزند | |

### مقایسه‌ای

| عملگر | معنا |
| ----- | ----- |
| `eq` / `ne` | برابر / نابرابر |
| `in` / `nin` | مقدار یکی از فهرست است / هیچ‌کدام نیست |
| `contains` | آرایه شامل مقدار است، یا رشته شامل آن است |
| `gt` `gte` `lt` `lte` | عددی؛ ارقام فارسی تبدیل می‌شوند |
| `exists` | مسیر به چیزی می‌رسد |
| `empty` | می‌رسد ولی پاسخ خالی است |
| `filled` | به یک پاسخ واقعی می‌رسد |

**«هر تطابقی برنده است.»** روی مسیر پیمایشی، `eq` می‌پرسد «آیا هر ردیفی
تطابق دارد؟» — که همان چیزی است که از `vehicles[].type == "کامیون"` می‌خواهید.

### تجمیعی بین ردیفی

این‌ها همان چیزی هستند که بررسی‌های مشورتی فرم QA را بدون نیاز به زبان عبارتی
ممکن می‌کنند.

| عملگر | چه زمانی درست است |
| ----- | ----------------- |
| `anyIn` | هر مقدارِ حل‌شده یکی از `value` است |
| `everyIn` | همهٔ مقادیر یکی از `value` هستند |
| `someTrue` | هر مقدار `true` است |
| `someFalse` | هر مقدار `false` است |
| `count` | تعداد ردیف‌ها با `gte` / `lte` سازگار است |

### معنی گروه خالی

این‌ها عمدی‌اند، نه بی‌دقتی:

| عملگر | گروه خالی | چرا |
| ----- | --------- | ---- |
| `anyIn` | `false` | هیچ‌کدام مصدوم نبودند |
| `everyIn` | `true` | هیچ‌کدام قید را نقض نکردند |
| `count` (gte 1) | `false` | هیچ ردیفی ثبت نشده |
| `count` (بدون کران) | `false` | شمارشِ بدون کران چیزی را اثبات نمی‌کند |

## چهار سازوکار، همراه با نمونه

### ۱. نمایش یا پنهان‌سازی فیلد — `visibleWhen`

نوع بار فقط برای وسایل سنگین معنا دارد:

```jsonc
{
  "key": "cargo",
  "label": "نوع بار",
  "visibleWhen": { "op": "in", "path": "vehicleType",
                   "value": ["کامیون", "تریلی", "تانکر حمل مواد خطرناک"] },
  "requiredWhen": { "op": "in", "path": "vehicleType",
                    "value": ["کامیون", "تریلی", "تانکر حمل مواد خطرناک"] }
}
```

### ۲. نمایش مجموعه فیلدهای کاملاً متفاوت

هر گزینهٔ جایگزین را در `group` خودش بگذارید و هر گروه را شرطی کنید. این همان
الزام «نمایش مجموعه فیلدهای متفاوت بر اساس مقدار انتخاب‌شده در فیلد قبلی» است:

```jsonc
{ "kind": "group", "key": "nationalPlate", "visibleWhen":
    { "op": "eq", "path": "plateType", "value": "ملی" },
  "children": [ /* ۲ رقم، حرف، ۳ رقم، ۲ رقم */ ] },

{ "kind": "group", "key": "motorcyclePlate", "visibleWhen":
    { "op": "eq", "path": "plateType", "value": "موتورسیکلت" },
  "children": [ /* ۳ رقم، ۵ رقم */ ] }
```

### ۳. تغییر گزینه‌های فیلد بعدی — `optionsFilter`

`optionsFilter` همان قطعه‌ای است که *انتخاب‌های* فیلد بعدی را به پاسخ فیلد قبلی
وابسته می‌کند:

```jsonc
{
  "key": "support",
  "options": { "kind": "literal", "items": [
    { "value": "اورژانس ۱۱۵", "label": "اورژانس ۱۱۵" },
    { "value": "آتش‌نشانی", "label": "آتش‌نشانی" },
    { "value": "جرثقیل",  "label": "جرثقیل" }
  ]},
  "optionsFilter": {
    "mode": "dynamic",
    "rule": { "op": "eq", "path": "hazmat", "value": "بله" },
    "values": ["آتش‌نشانی", "جرثقیل"]
  }
}
```

تا وقتی `hazmat` برابر «بله» است، فقط همان دو گزینه ارائه می‌شود. فیلتری که با
هیچ‌چیز تطابق ندارد **فهرست خالی** می‌دهد، نه فهرست کامل — نمایش «گزینه‌ای
نیست» ایمن‌تر از فهرست کشویی است که انتخاب‌های نامعتبر را ارائه می‌دهد.

| `mode` | رفتار |
| ------ | ------ |
| `all` | بدون محدودسازی (پیش‌فرض) |
| `static` | همیشه محدود به `values` |
| `dynamic` | فقط تا وقتی `rule` برقرار است، محدود به `values` |

### ۴. پاک‌کردن پاسخ وابسته — `clearOnChange`

تعویض نوع پلاک، پلاک ملی چهارقسمتی را در فیلدی جا می‌گذارد که حالا دو رقم
انتظار دارد. وابستگی را اعلام کنید و موتور آن را حذف می‌کند:

```jsonc
{
  "key": "plateType",
  "label": "نوع پلاک",
  "clearOnChange": ["plate_national", "plate_motorcycle", "plate_free"]
}
```

پاک‌سازی‌ها **تعدیی** هستند (a → b → c هر دو را پاک می‌کند) و **مقاوم در برابر
چرخه** (تعریفی که a → b → a اعلام کند متوقف می‌شود، نه اینکه بی‌نهایت بچرخد).
انتخاب دوبارهٔ همان مقدار از پیش انتخاب‌شده بی‌اثر است، پس لمس یک گزینهٔ انتخاب‌شده
بخش‌های واردشده را پاک نمی‌کند.

مسیرها **نسبت به ردیف خودِ فیلد تغییرکرده** نوشته می‌شوند، پس `clearOnChange`
درون یک وسیله فقط همان وسیله را تحت تأثیر قرار می‌دهد.

## دو سطح: خطا و هشدار

نمونهٔ QA بین `errors()` (جلوگیر) و `warnings()` (مشورتی) تمایز می‌گذارد. موتور هم
همین‌طور.

**خطاها** از `requiredWhen` و محدودیت‌های عددی می‌آیند:

```jsonc
{ "key": "severity", "requiredWhen": { "op": "always" } }
```

**هشدارها** برای هر فیلد تعریف می‌شوند و هرگز جلوگیری نمی‌کنند:

```jsonc
{
  "key": "severity",
  "validation": { "warnings": [{
    "rule": { "op": "and", "rules": [
      { "op": "eq", "path": "severity", "value": "خسارتی" },
      { "op": "or", "rules": [
        { "op": "anyIn", "path": "vehicles[].driver.health",      "value": ["مصدوم", "فوتی در صحنه"] },
        { "op": "anyIn", "path": "vehicles[].passengers[].health", "value": ["مصدوم", "فوتی در صحنه"] },
        { "op": "anyIn", "path": "pedestrians[].health",          "value": ["مصدوم", "فوتی در صحنه"] }
      ]}
    ]},
    "message": "شدت خسارتی با وجود مصدوم یا فوتی سازگار نیست."
  }]}
}
```

به فارسی: «شدت خسارتی است **و** (راننده **یا** سرنشین **یا** عابر مصدوم/فوتی
است)». در نمونهٔ اصلی این یک هشدار است — مأمور گزارش را ثبت می‌کند و به بازبینی
ترغیب می‌شود. اینجا هم هشدار است، هرگز مانع.

هشدار دوم، روی `support`: وسیله‌ای به جرثقیل نیاز دارد ولی درخواست نشده.

```jsonc
{ "op": "and", "rules": [
  { "op": "anyIn", "path": "vehicles[].mobility", "value": ["نیاز به جرثقیل"] },
  { "op": "not", "rule": { "op": "contains", "path": "support", "value": "جرثقیل" } }
]}
```

## شرطی‌سازی صفحه

یک صفحه می‌تواند شرطی باشد و همین‌طور یک گام کامل ناپدید می‌شود:

```jsonc
{ "key": "facilityDamage", "title": "آسیب تجهیزات راه", "order": 8,
  "visibleWhen": { "op": "eq", "path": "hasDamage", "value": "بله" },
  "sections": [ /* … */ ] }
```

> **پرسشِ شرط‌کننده را روی صفحه‌ای بگذارید که همیشه دیده می‌شود.** اگر
> `hasDamage` را روی صفحه‌ای بگذارید که خودش شرطی است، پاسخ‌دادن به آن ناممکن
> می‌شود — چون آن صفحه فقط پس از پاسخ‌دادن ظاهر می‌شود.

## تضمین‌های مقاومت

`evalRule` **هرگز خطا نمی‌دهد**. شرط نامعتبر به `false` ارزیابی می‌شود.

| ورودی | نتیجه |
| ----- | ------ |
| عملگر ناشناخته | `false` |
| `and` با فرزند گمشده | `false` |
| `not` با فرزند گمشده | `true` |
| `path` خالی | `false` |
| ۴۰ سطح `not` | بدون سرریز پشته |

یک تعریف خراب به فرمی با شرطی که هرگز برقرار نمی‌شود تبدیل می‌شود — نمی‌تواند
اپ میدانی را کرش کند. بک‌اند همچنان شرط خراب را در `activate` رد می‌کند و فرم‌ساز
دربارهٔ مسیرهایی که resolve نمی‌شوند هشدار می‌دهد، چون شرطی که بی‌صدا هرگز برقرار
نمی‌شود بدتر از خطاست: نویسنده فکر می‌کند فیلدش شرطی است و نیست.

## دام‌ها

۱. **مسیر معلق به `false` ارزیابی می‌شود، نه به خطا.** تابع
   `unresolvedRulePaths` در `front/src/components/org/forms/rule-editor.ts`
   این موارد را به نویسنده اعلام می‌کند.
۲. **`anyIn` روی گروه خالی `false` است.** اگر می‌خواهید «هیچ وسیله‌ای ثبت نشده»
   را شرط کنید، از `count` با `lte` استفاده کنید، نه `anyIn`.
۳. **شرط‌ها درون گروه تکرارشونده، ردیف را می‌بینند.**
   `{ "op": "eq", "path": "type" }` درون یک وسیله، type همان وسیله را می‌خواند.
۴. **فیلد پنهان هرگز الزامی نیست.** الزام هنگام نامرئی بودن نادیده گرفته می‌شود، پس
   پنهان‌کردن یک پرسش هرگز مأمور را قفل نمی‌کند.
۵. **رسیدن به خواهرها نیازمند مسیر کامل است.** از ریشه `vehicles[].type` و درون
   ردیف وسیله، `type` کافی است.
