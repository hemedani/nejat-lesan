# ۰۵ — راهنمای طراحی فرم

چگونه یک فرم بسازیم: یا در رابط کاربری فرم‌ساز، یا با نوشتن مستقیم یک تعریف.

## مدل ذهنی

یک تعریف، درختی از **صفحه‌ها ← بخش‌ها ← گره‌ها** است. سه نوع گره:

| نوع | پاسخ دارد؟ | تکرار می‌شود؟ |
| ---- | ----------- | -------------- |
| `field` | بله | خیر |
| `group` | خیر | خیر |
| `repeatable` | خیر | بله، و تودرتو |

دو پرسش، بیشتر تصمیم‌های طراحی را پاسخ می‌دهند:

۱. **آیا این باید یک صفحه باشد؟** صفحه یعنی گامی که مأمور به آن می‌رود. برای
هر مرحلهٔ متمایز از کار مأمور یکی بگذارید. اگر بخشی نیاز به عنوان جدا و
«مرحله بعد» جدا دارد، صفحه است.
۲. **آیا مأمور چندتا از این‌ها وارد می‌کند؟** اگر بله، `repeatable` است. اگر هر
نمونه پرسش‌های فرعی خودش را دارد، آن پرسش‌ها در `children` همان گروه می‌آیند — و
یکی از آن فرزندان خودش می‌تواند یک گروه تکرارشوندهٔ دیگر باشد.

## ساخت در رابط کاربری

فرم‌ساز در `front/src/components/org/forms/` قرار دارد.

```
FormBuilder.tsx     درخت صفحه/بخش/فیلد، ذخیره، فعال‌سازی، تکثیر
NodeTree.tsx        درخت + پالت فیلد + جابه‌جایی با ↑/↓
FieldEditor.tsx     ویرایشگر ویژگی هر نوع، شرط‌ها، پاک‌سازی‌های وابسته
RuleEditor.tsx      سازندهٔ تعاملی شرط با بازخوانی فارسی
LivePreview.tsx     رندر تعریف با موتور واقعی
form-types.ts       توابع خالص: کارخانه‌ها، تغییرناپذیری، بازرسی
rule-editor.ts      ساخت شرط + describeRule (فارسی)
```

### گردش کار

۱. **افزودن صفحه.** هر صفحه با یک بخش شروع می‌شود.
۲. **افزودن فیلد** از پالت (۱۵ نوع) یا یک **گروه تکرارشونده** یا یک **گروه ساده**.
۳. **جابه‌جایی** با ↑/↓. کشیدن و رها کردن عمداً استفاده نشده: در
   `front/AGENTS.md` کتابخانهٔ drag ثبت نشده، `ProcessBuilder` از قبل جابه‌جایی با
   دکمه را جا انداخته، و افزودن `@dnt-kit` برای یک صفحه پیچیدگی بی‌دلیل بود.
۴. **انتخاب گره** برای ویرایش ویژگی‌ها: عنوان، نوع، توضیح، پیام خطای دلخواه،
   گزینه‌ها، شرط‌ها، پاک‌سازی‌های وابسته.
۵. **نوشتن شرط‌ها** در سه جایگاه. هر شرط یک بازخوانی زندهٔ فارسی نشان می‌دهد —
   «معنی شرط: …» — تا مطمئن شوید ماشین درست متوجه شده است.
۶. **بررسی زبانهٔ پیش‌نمایش.** با موتور واقعی اجرا می‌شود، پس آنچه می‌بینید همان
   چیزی است که مأمور می‌گیرد.
۷. **ذخیره.** سپس **فعال‌سازی** برای انتشار.

### پیش‌نمایش، ماکت نیست

`LivePreview` همان توابع `isNodeVisible`، `resolveOptions` و `validateForm` را
calling می‌کند که اپ موبایل صدا می‌زند. یک پیاده‌سازی جداگانه برای پیش‌نمایش
از موتور جدا می‌افتاد و به‌سکوت گمراه‌کننده می‌شد، پس چنین چیزی وجود ندارد.

در پیش‌نمایش به یک پرسش پاسخ دهید و ببینید فیلدهای وابسته ظاهر و ناپدید
می‌شوند.

### فعال‌سازی، یک دروازه است

**فعال‌سازی** اعتبارسنج ساختاری سمت سرور را اجرا می‌کند و می‌تواند رد کند:

- تعریفی بدون صفحه
- کلیدهای تکراری
- عملگر شرط ناشناخته
- عملگر مسیردار بدون `path`
- مدل `reference` که وجود ندارد یا رکورد ندارد

رد شدن، تعریف را **پیش‌نویس** نگه می‌دارد، با پیام فارسی که می‌گوید چه چیزی
باید اصلاح شود.

تعریف **فعال** فقط‌خواندنی است. برای تغییر، آن را بایگانی یا تکثیر کنید — این
عمدی است: ممکن است مأموران پیش‌نویس‌هایی بر پایهٔ نسخهٔ جاری در دست داشته باشند.

> فرم‌ساز روی `/forms` در دسترس است و از نوار کناری پنل سرپرست سازمان و سرپرست
> واحد هم به آن لینک داده شده (بخش «فرم‌ساز»، وقتی ماژول `forms` برای سازمان روشن
> باشد). سازمان از `user.roles[]` گرفته می‌شود و Ghost/Manager که نقش سازمانی
> ندارند، سازمان را دستی انتخاب می‌کنند.

## نوشتن تعریف به‌صورت دستی

برای تست‌ها، داده‌های اولیه و فرم‌های تحت کنترل نسخه مفید است.

```ts
import type { FormDefinition } from '@forms';

export const myForm: FormDefinition = {
  schemaVersion: 1,
  name: 'فرم بازرسی',
  pages: [{
    key: 'intro',
    title: 'اطلاعات اولیه',
    order: 1,
    sections: [{
      key: 'introSection',
      title: 'عمومی',
      order: 1,
      nodes: [
        {
          kind: 'field',
          key: 'severity',
          type: 'choice_group',
          label: 'شدت',
          order: 1,
          requiredWhen: { op: 'always' },
          options: { kind: 'literal', items: [
            { value: 'low', label: 'کم' },
            { value: 'high', label: 'زیاد', tone: 'danger' },
          ]},
        },
        {
          kind: 'field',
          key: 'escalateTo',
          type: 'select',
          label: 'ارجاع به',
          order: 2,
          // فقط وقتی شدت زیاد است ارائه می‌شود
          options: { kind: 'literal', items: [
            { value: 'supervisor', label: 'سرپرست' },
            { value: 'hq', label: 'ستاد' },
          ]},
          optionsFilter: {
            mode: 'dynamic',
            rule: { op: 'eq', path: 'severity', value: 'high' },
            values: ['supervisor', 'hq'],
          },
        },
      ],
    }],
  }],
};
```

### سیاههٔ تعریفی که کار می‌کند

- [ ] هر `key` در کل تعریف یکتاست — شرط‌ها با کلید فیلد را نشان می‌دهند
- [ ] `order` متوالی است تا خوانایی حفظ شود
- [ ] پرسشی که پرسش دیگری را آشکار می‌کند روی **صفحهٔ همیشه‌دیدنی** است
- [ ] گزینه‌ها `value` پایدار دارند، نه برچسبی که ممکن است بازنویسی شود
- [ ] فیلدهایی که روی یک فیلد واقعی مدل نگاشت می‌شوند `binding` دارند
- [ ] هر binding از نوع `relation`/`dto` روی فیلد **`reference`** است — یک گزینهٔ
      literal نمی‌تواند رابطهٔ ObjectId را برآورده کند
- [ ] هر هدف binding واقعاً وجود دارد: رابطه‌ای که مدل هدف اعلام می‌کند، یا فیلدی
      واقعی از یک DTO واقعی (فرم‌ساز هر دو را از اسکیمای زنده مشتق می‌کند)
- [ ] فرم یک `icon` از واژگان مشترک ۸۰ نامی دارد، تا مأمور آن را در انتخابگر
      پیش از خواندن عنوان تشخیص دهد
- [ ] `form_kind` با مدلی که پاسخ‌ها به آن می‌رود هم‌خوان است: `accident` برای
      برخوردها، `incident_report` برای هر چیز دیگر. یک سازمان می‌تواند یک فرم فعال
      تصادف و هر تعداد فرم گزارش داشته باشد.
- [ ] پاسخ‌هایی که با تغییر والد بی‌معنا می‌شوند `clearOnChange` دارند
- [ ] بررسی‌های بین‌ردیفی منطقی `warnings` هستند، نه errors
- [ ] مدل‌های مرجع وجود دارند و رکورد دارند (فرم‌ساز هشدار می‌دهد؛ `activate`
      رد می‌کند)

`activate` پیش‌نویسی را که در بررسی binding، آیکون یا مرجع رد شود نمی‌پذیرد و آن
پیش‌نویس باقی می‌ماند. پس همهٔ موارد بالا در زمان انتشار اعمال می‌شوند، نه در میدان.

## نمونه‌های پرکاربرد

### یک بخش شرطی

```jsonc
{
  "kind": "group", "key": "damageSection", "label": "آسیب",
  "visibleWhen": { "op": "eq", "path": "hasDamage", "value": "بله" },
  "children": [ /* … */ ]
}
```

### فهرستی با حداقل

```jsonc
{ "kind": "repeatable", "key": "vehicles", "label": "وسیله نقلیه",
  "minItems": 1, "children": [ /* … */ ] }
```

`minItems` یک بار برای کل گروه بررسی می‌شود، نه برای هر ردیف.

### هشدار بین‌ردیفی

```jsonc
{
  "key": "support",
  "validation": { "warnings": [{
    "rule": { "op": "and", "rules": [
      { "op": "anyIn", "path": "vehicles[].mobility", "value": ["نیاز به جرثقیل"] },
      { "op": "not", "rule": { "op": "contains", "path": "support", "value": "جرثقیل" } }
    ]},
    "message": "وسیله نیاز به جرثقیل دارد اما این پشتیبانی انتخاب نشده است."
  }]}
}
```

### زیرفرم‌های متفاوت بر اساس پاسخ قبلی

[۰۳ شرط‌ها](./03-rules-and-conditions-fa.md#۲-نمایش-مجموعه-فیلدهای-کاملاً-متفاوت)
را ببینید.

### ارجاع بین‌گروهی

رکورد آسیبی که به وسیله‌ای در گروه دیگر اشاره می‌کند، یک `select` است که
گزینه‌هایش هنگام رندر از فهرست وسایل پر می‌شود:

```jsonc
{ "key": "damage_vehicleId", "type": "select", "label": "وسیله مرتبط",
  "options": { "kind": "literal", "items": [] } }
```

> این مورد اعلان شده ولی **هنوز هنگام رندر پر نمی‌شود** — سند
> [۰۸ وضعیت](./08-migration-and-status-fa.md) را ببینید.

نیست؛ بنابراین به‌عنوان تست نگه داشته می‌شود، نه دادهٔ اولیه.
