# ۰۷ — بررسی فرم تصادف QA

نمونهٔ مرجع تیم کیفیت، `qa_docs/QA_AR/Accident_Report_App.html` است با ۷۳۹ خط
جاوااسکریپت دست‌نویس. این نمونه **به‌طور کامل** به‌صورت یک تعریف بازتولید شده
است:

```
shared/form-engine/src/qa-accident-form.ts        خودِ تعریف
mobile/src/domain/qa-accident-form.ts              شیم باز-اکسپورت به همان فایل
mobile/src/domain/qa-accident-form.test.ts         ۳۵ تست پذیرش
```

تعریف در موتورِ مشترک زندگی می‌کند، نه در درختِ منبعِ یک اپ، چون هم تستِ پذیرشِ
موتور است و هم فرمِ تصادفی‌ای که بک‌اند برای یک سازمان دمو فعال می‌کند، در حالی که
موبایل آن را رندر می‌کند. مسیرِ موبایل حالا فقط یک باز-اکسپورتِ تک‌خطی است، پس یک
artefact داریم، نه دو تا.

این سند هر رفتار نمونهٔ اصلی را به سازوکاری که اکنون آن را پیاده‌سازی می‌کند نگاشت
می‌دهد. آن جدول معیار پذیرش است: **هر سطر اعلانی است، بدون هیچ کد اجرایی پشت
آن.** رفتاری که برای بیان شدن به کد نیاز داشته باشد یعنی موتور به اندازهٔ کافی
عمومی نیست، و آن شکاف متعلق به موتور است — نه به یک تعریف خاص.

## کنار هم

| نمونهٔ اصلی | سازوکار | کجا |

| وسیلهٔ سنگین ← انتخاب نوع بار | `visibleWhen` + `requiredWhen` | `cargo` |

## تعویض پلاک — سخت‌ترین الزام

تابع `plateFields` نمونهٔ اصلی بر اساس `plateType` بین چهار شکل کاملاً متفاوت
جابه‌جا می‌شود. اینجا هر شکل، فیلد خودش است که با شرط کنترل می‌شود:

```
plate_national      ملی              → ۲ رقم / حرف / ۳ رقم / ۲ رقم
plate_motorcycle    موتورسیکلت        → ۳ رقم / ۵ رقم
plate_free          منطقه آزاد         → کد منطقه / ۵ رقم
plate_temporary_*   گذر موقت / خاص     → شناسه / شماره
```

تعویض نوع، بقیه را پاک می‌کند، چون شکل‌ها با هم سازگار نیستند:

```jsonc
{
  "key": "plateType",
  "clearOnChange": ["plate_national", "plate_motorcycle", "plate_free"]
}
```

## نوع بار فقط برای وسایل سنگین

تابع کمکی `heavy(v)` در نمونهٔ اصلی:

```ts
['وانت بار','مینی‌بوس','اتوبوس','کامیونت','کامیون','تریلی','تانکر حمل مواد خطرناک','خودروی آتش‌نشانی']
```

به یک قاعدهٔ اعلانی تبدیل می‌شود:

```jsonc
{ "op": "in", "path": "vehicleType", "value": [ … ] }
```

با همان فهرست، هم روی `visibleWhen` و هم روی `requiredWhen`.

## هشدارهای بین‌ردیفی

سه مورد از `warnings()` نمونهٔ اصلی عیناً باقی مانده‌اند.

**شدت خسارتی با وجود مصدوم در پرونده:**

```jsonc
{ "op": "and", "rules": [
  { "op": "eq", "path": "severity", "value": "خسارتی" },
  { "op": "or", "rules": [
    { "op": "anyIn", "path": "vehicles[].driver.health",       "value": ["مصدوم", "فوتی در صحنه"] },
    { "op": "anyIn", "path": "vehicles[].passengers[].health", "value": ["مصدوم", "فوتی در صحنه"] },
    { "op": "anyIn", "path": "pedestrians[].health",           "value": ["مصدوم", "فوتی در صحنه"] }
  ]}
]}
```

این همان بررسی‌ای است که اگر `anyIn` وجود نداشت، ما را ناچار به زبان عبارتی
می‌کرد. سه خط JSON است.

**وسیله‌ای به جرثقیل نیاز دارد که درخواست نشده** — محدود به ردیف وسیله، تا
هشدار وسیلهٔ ۱ با پاسخ وسیلهٔ ۲ داده نشود:

```jsonc
{ "op": "and", "rules": [
  { "op": "eq",   "path": "mobility", "value": "نیاز به جرثقیل" },
  { "op": "not", "rule": { "op": "contains", "path": "support", "value": "جرثقیل" } }
]}
```

**مدرک ناقص** — نمونهٔ اصلی وسایل و آسیب‌های بدون عکس را علامت می‌زند.

## نگاشت‌ها — چرا نمودارها کار می‌کنند

دو فیلد روی روابط typed در `accident` نگاشت می‌شوند:

```jsonc
{ "key": "severity",  "binding": { "kind": "relation", "path": "type" } }
{ "key": "collision", "binding": { "kind": "relation", "path": "collision_type" } }
{ "key": "lighting",  "binding": { "kind": "relation", "path": "light_status" } }
{ "key": "date_of_accident", "binding": { "kind": "pure", "path": "date_of_accident" } }
```

هر ۳۴ اکشن تحلیل و نمودار موجود، همان فیلدهایی را می‌خوانند که همیشه
می‌خواندند.

## تغییرات طراحی حین بازتولید

بازتولید نمونه، دو مشکل ساختاری را آشکار کرد که هر دو رفع شدند:

**رانندگان فهرستی جدا بودند.** نمونهٔ اصلی وسایل و رانندگان را در برگه‌های جدا با
کلید اندیس نگه می‌دارد، که می‌تواند از هم جدا بیفتد — راننده می‌تواند به اشتباه به
وسیلهٔ دیگری بچسبد، و دو فهرست کلیدهای تکراری دارند که هر شرطی را که آن‌ها را
نام ببرد می‌شکند. راننده به یک گروه تکرارشوندهٔ `maxItems: 1` درون هر وسیله تبدیل
شد. یک ردیف، یک راننده، بدون کلید تکراری.

**گیت آسیب دایره‌ای بود.** `hasDamage` ابتدا روی صفحه‌ای بود که خودش شرطی است —
تنها پس از `hasDamage === 'بله'` ظاهر می‌شود، پس پاسخ‌دادن به آن ناممکن بود. حالا
روی صفحهٔ `emergencyActions` است که همیشه دیده می‌شود.

## هنوز بازتولید نشده

| رفتار نمونهٔ اصلی | وضعیت |
| ------------------ | ------ |
| پین نقشه، GPS، لایه ماهواره‌ای، چسباندن به جاده | فیلد `location` اعلام شده؛ گرفتن در صفحهٔ اختصاصی موجود انجام می‌شود، هنوز به فیلد فرم وصل نشده |
| پیوست تصویر/ویدئو/PDF برای هر ردیف | فیلد `file` اعلام شده؛ رسانه در صفحهٔ رسانهٔ موجود گرفته می‌شود، هنوز وصل نشده |
| نمایش فاصلهٔ مأمور تا واقعه و دقت GPS | نوع فیلد `computed` وجود دارد؛ این نمایش‌های خاص هنوز اعلام نشده‌اند |
| کیلومتر/متر از محور راه | خود نمونهٔ اصلی این را نیازمند داده‌های GIS علامت زده است |

## اجرای تست‌های پذیرش

```bash
cd mobile && npx vitest run src/domain/qa-accident-form.test.ts
```

۳۵ تست پوشش می‌دهد: ساختار نُه‌صفحه‌ای، کلیدهای یکتا، نبود نوع فیلد پشتیبانی‌نشده،
گروه‌های تکرارشوندهٔ تودرتو، نگاشت‌ها، هر قاعدهٔ نمایش شرطی، هر تعویض پلاک، گیت نوع
بار، رنگ‌بندی، هر هشدار که فعال و پاک می‌شود، پاک‌سازی‌های وابسته، `minItems`، و
اعتبارسنجی یک گزارش کامل، صفحه به صفحه.

اگر هرکدام از این‌ها برای بیان شدن به کد نیاز داشته باشد، یعنی موتور به اندازهٔ
کافی عمومی نیست — و دقیقاً به همین دلیل این فایل یک تست است، نه دادهٔ اولیه.
