# ۰۱ — نمای کلی و معماری

## مسئله‌ای که حل می‌شود

پیش از موتور فرم‌ساز، تنها فرم مبتنی بر تعریف در سامانه لسن، `accident_process`
بود. این فرم فقط یک چیز را به‌خوبی بیان می‌کرد: ویزاردی از سؤالات انتخابی که
پاسخ‌هایشان از یکی از **ده مدل مرجع ثابت** می‌آمد
(`back/src/accident_process/questionRegistry.ts`).

همین سقف، سه محدودیت عملی ایجاد می‌کرد:

۱. **بدون انواع فیلد.** بدون متن، عدد، تاریخ، فایل، نقشه یا ورودی مرکب. فقط
«چند شناسه از `collision_type` انتخاب کن».
۲. **بدون شرط.** تنها منطق هر سؤال `required: boolean` بود، و آن پرچم هرگز در
سرور اعمال نمی‌شد — فقط در کلاینت موبایل.
۳. **بدون گروه‌بندی.** بدون ردیف تکرارشونده، پس بدون فهرست وسایل و بدون
سرنشین برای هر وسیله.

وقتی تیم کیفیت فرم مرجع واقع‌گرایی ارائه کرد
(`qa_docs/QA_AR/Accident_Report_App.html` با ۷۳۹ خط)، فاصله آشکار بود. آن نمونهٔ
اولیه به مواردی از این جنس نیاز دارد:

- `plateType` که یکی از **چهار زیرفرم کاملاً متفاوت** را انتخاب می‌کند
- `hasDamage === 'بله'` که کل بخش آسیب را آشکار می‌کند
- پاسخ‌های `emergency` که گزینه‌های پشتیبانی در دسترس را تغییر می‌دهند
- `vehicles[] → راننده + سرنشین[]` — یعنی گروه‌های تکرارشونده تودرتو
- `errors()` که جلوی پیشروی را می‌گیرد و `warnings()` که نمی‌گیرد

هیچ‌کدام در ساختار قبلی جا نمی‌شود. بنابراین موتور ساخته شد.

## موتور چیست

یک **بستهٔ TypeScript واحد و بدون وابستگی** که معنای تعریف فرم را در اختیار
می‌گذارد:

```
shared/form-engine/
├── src/
│   ├── types.ts       # ساختار تعریف (صرفاً نوع، بدون کد اجرایی)
│   ├── paths.ts       # نشانی‌دهی پاسخ‌ها: "vehicles[].passengers[].health"
│   ├── rules.ts       # تابع evalRule — ارزیاب شرط
│   ├── traverse.ts    # تابع walkNodes — پیمایش درخت با دامنه ردیف
│   ├── conditions.ts  # نمایش، الزام، محدودسازی گزینه‌ها
│   ├── validate.ts    # اعتبارسنجی دو سطحی: خطا و هشدار
│   ├── cascade.ts     # clearOnChange — پاک‌سازی پاسخ‌های وابسته
│   ├── bindings.ts    # نگاشت پاسخ‌ها onto فیلدهای typed در accident
│   ├── snapshot.ts    # پهن‌کردن پاسخ‌ها به سطرهای dynamic_answers
│   └── icons.ts       # واژگان مشترک ۸۰ آیکون Phosphor (داده، نه کامپوننت)
└── test/              # ۱۴۰ تست
```

هیچ‌کدام از فایل‌های این بسته، React یا Deno یا Expo را ایمپورت نمی‌کنند.
همه توابع خالص‌اند و روی اشیای ساده کار می‌کنند.

## چرا یک بستهٔ مشترک

اپ موبایل باید **در نبود شبکه** تصمیم بگیرد چه چیزی نمایش داده شود، چه چیزی
الزامی است و چه چیزی معتبر است. بک‌اند هنگام رسیدن گزارش، همان پرسش‌ها را دوباره
تصمیم می‌گیرد. اگر این دو پیاده‌سازی هرگز اختلاف پیدا کنند، ممکن است مأمور
فرمی را پر کند که سرور آن را رد می‌کند — یا بدتر، گزارشی ثبت کند که باید
جلویش گرفته می‌شد.

بنابراین ارزیاب یک بار نوشته و سه بار مصرف می‌شود:

| مصرف‌کننده | چگونه از موتور استفاده می‌کند |
| ----------- | ------------------------------ |
| `back/` | `validateForm` هنگام ثبت — مرجع نهایی |
| `mobile/` | `validateForm` به‌صورت آفلاین — راهنمای مأمور، با همان نتیجه |
| `front/` | `validateForm` در پیش‌نمایش زندهٔ فرم‌ساز — همان چیزی که کاربر می‌بیند |

این یک الزام درستی است، نه صرفاً تلاش برای حذف تکرار. در `mobile/AGENTS.md` هم
آمده است: *«اعتبارسنجی و انتقال‌ها باید در منطق دامنه‌ای قابل تست باشند.»*

برای ایمپورت از نام `@forms` استفاده کنید:

```ts
import { validateForm, visiblePages, evalRule } from "@forms";
```

## جریان داده

```
        form_definition (MongoDB)
                 │
                 │ getForPatrol  ── فهرست گزینه‌های reference را حل می‌کند
                 │                ── فهرست‌های مجاز (allowedIds) را حذف می‌کند
                 ▼
        ┌──────────────────┐
        │  رندرکننده موبایل │  ← قابل کار در حالت آفلاین
        │  walkNodes       │
        │  isNodeVisible   │
        │  validateForm    │
        └────────┬─────────┘
                 │ answers (درخت تودرتو، همان‌طور که ارسال شده)
                 ▼
        ┌──────────────────┐
        │  بک‌اند           │  ← مرجع نهایی
        │  validateForm    │  همان تابع، همان نسخهٔ تعریف
        │  buildBindings   │  → فیلدهای typed روی مدل هدف
        └────────┬─────────┘
                 ▼
        accident (روابط typed + DTO) → نمودارها و تحلیل‌های موجود
      یا incident_report (روابط خودش) → چرخهٔ بازبینی گزارش
```

اینکه نگاشت روی کدام مدل بنشیند را `form_kind` فرم تعیین می‌کند، نه محتوای payload.
دو مدل روابط متفاوتی اعلام می‌کنند، پس payload تصادفی که به اکشن گزارش فرستاده شود
 outright رد می‌شود.

## پاسخ‌ها و نگاشت‌ها

پاسخ‌ها به‌صورت درختی تودرتو مطابق ساختار تعریف ذخیره می‌شوند:

```jsonc
{
  "severity": "جرحی",
  "vehicles": [
    { "vehicleType": "سواری", "passengers": [{ "health": "مصدوم" }] }
  ]
}
```

این درخت **برای خودِ فرم** مرجع است. جداگانه، هر فیلد می‌تواند یک `binding`
اعلام کند که مقدارش را به یک فیلد typed واقعی روی مدل هدف نگاشت می‌کند:

```jsonc
{ "key": "severity", "binding": { "kind": "relation", "path": "type" } }
```

به همین دلیل هر اکشن تحلیل و نمودار موجود بدون تغییر کار می‌کنند: مقدار
`severity` روی `accident.type` و `collision` روی `accident.collision_type`
می‌نشیند، و نمودارها همان چیزی را می‌خوانند که همیشه می‌خواندند. درخت عمومی
چیز جدیدی است؛ نگاشت typed چیز جدیدی نیست.

هر binding فقط هنگام **فعال‌سازی** بررسی می‌شود و باید چیزی واقعی را نام ببرد: رابطه‌ای
که مدل هدف اعلام می‌کند (مشتق‌شده از اسکیمای زندهٔ Lesan، نه یک فهرست دستی) یا فیلدی
واقعی از یک DTO واقعی. binding از نوع `relation` یا `dto` هم فقط روی فیلد
`reference` مجاز است — یک گزینهٔ literal نمی‌تواند رابطهٔ ObjectId را برآورده کند.
گرفتن این خطا هنگام انتشار فرم همان چیزی است که نمی‌گذارد مأمور بعد از پر کردن فرم
کنار جاده بفهمد که فرم خراب بوده است.

پاسخ‌هایی که به چیزی bind نمی‌شوند هم از بین نمی‌روند: `form_answers` کل درخت را
عیناً نگه می‌دارد و `dynamic_answers` آن را تخت mirror می‌کند، پس یک گزارش هرگز به
آنچه تصادفاً قابل‌کوئری بوده تقلیل پیدا نمی‌کند.

## تصمیم‌های طراحی که باید بدانید

**شرط‌ها به‌شکل اعلانی، نه عبارتی.** شرط‌ها یک درخت JSON هستند
(`{op: "and", rules: [...]}`) و نه رشته‌هایی مانند `severity == 'fatal' && …`.
نه `eval` وجود دارد، نه پارسری که باید امن شود، و نه سطح حملهٔ تزریق. فرم‌ساز
می‌تواند هر شرط را به‌صورت جمله‌ای فارسی به نویسنده نشان دهد. عملگرهای تجمیعی
(`anyIn`، `everyIn`، `count`، `someTrue`، `someFalse`) بررسی‌های بین‌ردیفی‌ای را
پوشش می‌دهند که در غیر این صورت ما را ناچار به زبان عبارتی می‌کرد.

**تودرتویی نامحدود.** `RepeatableNode` شامل `ContentNode[]` است و یک
`RepeatableNode` می‌تواند شامل `RepeatableNode` دیگری باشد. همین، ساختار
`vehicles → راننده + passengers[]` را بدون طراحی schema اختصاصی برای هر شکل
بیان می‌کند.

**همیشه دو سطح.** نمونهٔ QA بین `errors()` (جلوگیر) و `warnings()` (مشورتی)
تمایز می‌گذارد. موتور هم همین‌طور است: `validateForm` مقدار
`{ errors, warnings, blockedPages }` برمی‌گرداند. هشدار هرگز جلوگیری نمی‌کند —
«جرثقیل لازم است ولی انتخاب نشده» باید مأمور را به بازبینی وادارد، نه اینکه
جلوی ثبت گزارش در کنار جاده را بگیرد.

**پنهان یعنی بی‌ربط.** گره نامرئی هرگز الزامی و هرگز نامعتبر نیست. این دام
کلاسیک فرم‌های شرطی است: پرسش پنهانی که همچنان الزامی مانده، مأمور را برای همیشه
از فرم قفل می‌کند.

**هرگز خطا نمی‌دهد.** یک شرط نامعتبر به `false` ارزیابی می‌شود. تعریف خراب
نباید بتواند صفحهٔ موبایل مأمور را در کنار جاده کرش کند.
