# ۰۴ — مرجع ای‌پی‌آی بک‌اند

نام اسکیما: **`form_definition`**. همهٔ اکشن‌ها از قرارداد لسن پیروی می‌کنند
(`{ service, model, act, details: { set, get } }`)، با هدر `token` احراز هویت
می‌شوند (بدون پیشوند `Bearer`) و پوشش استاندارد `{ success, body }` را برمی‌گردانند.

## اکشن‌ها

| اکشن | دسترسی | هدف |
| ---- | ------ | ---- |
| `add` | Manager، OrgHead، UnitHead (+ Ghost) | ساخت تعریف پیش‌نویس |
| `update` | Manager، OrgHead، UnitHead (+ Ghost) | جایگزینی کامل تعریف |
| `get` | هر کاربر احراز‌شده، **محدود به سازمان‌های خودش** | خواندن یک تعریف |
| `gets` | هر کاربر احراز‌شده، **محدود به سازمان‌های خودش** | فهرست، صفحه‌بندی و فیلتر |
| `count` | هر کاربر احراز‌شده، **محدود به سازمان‌های خودش** | شمارش برای صفحه‌بندی |
| `remove` | Manager، OrgHead، UnitHead (+ Ghost) | حذف (هرگز فرم فعال) |
| `activate` | Manager، OrgHead، UnitHead (+ Ghost) | اعتبارسنجی، بایگانی قبلی، انتشار |
| `duplicate` | Manager، OrgHead، UnitHead (+ Ghost) | کپی به‌صورت پیش‌نویس جدید |
| `getForPatrol` | هر کاربر احراز‌شده | تعریف فعال + گزینه‌های حل‌شده |
| `getReferenceOptions` | هر کاربر احراز‌شده | سطرهای گزینه برای یک مدل مرجع |
| `validate` | هر کاربر احراز‌شده، **محدود به سازمان‌های خودش** | ارزیابی شرط‌ها در سرور |

**Ghost همیشه مجاز است** و در آرایهٔ `levels` این اکشن‌ها نیامده است.
`grantAccess` (`back/utils/grantAccess.ts`) با
`if (levelIsInUser || user.level === "Ghost")` کوتاه‌می‌شود، پس Ghost از هر بررسی سطحی
عبور می‌کند، چه در فهرست باشد چه نباشد. همین معافیت برای گیت ماژول (هم سطح نصب و هم
سطح سازمان) هم برقرار است — `back/AGENTS.md` را ببینید. `FormAuthorGuard` در فرانت هم
دقیقاً همین چهار سطح را می‌پذیرد: Ghost، Manager، OrgHead، UnitHead.

`getForPatrol` و `validate` عمداً **بدون `grantAccess`** هستند: هم مأمور گشت و هم
سرِ سازمان باید بتوانند فرم را رندر و بررسی کنند. مجوز آنجا بر پایهٔ حل سازمان
است، نه سطح دسترسی.

با این حال هر چهار اکشن خواندن **محدود** هستند. هرکدام سازمان مؤثر را با
`orgFilterFor` → `getAllowedManagerOrgIds` حل می‌کنند، همان کمکی که
`accident_process.gets` استفاده می‌کند:

- Ghost و Manager بدون فیلتر عبور می‌کنند و می‌توانند بین سازمان‌ها بخوانند.
- بقیه به سازمان‌هایی محدود می‌شوند که عضو آن هستند. دادن `organizationId` خارج از
  این مجموعه خطای «شما به این سازمان دسترسی ندارید» می‌دهد.
- حذف `organizationId` وقتی چند سازمان در دامنه است، به‌جای فهرست همه، خطای
  «شناسه سازمان را مشخص کنید» می‌دهد.

`validate` برای تعریفی خارج از دامنهٔ فراخوان «فرم یافت نشد» برمی‌گرداند، تا فراخوان
نتواند از راه فهرست خطاها پرسش‌های سازمان دیگر را کشف کند. پوشش تست:
`back/test/form-definition-access-test.ts`.

## مدل‌ها

### form_definition

تعریف فرم در محدودهٔ یک سازمان.

```ts
{
  name: string;
  description?: string;
  icon: string;                              // یکی از ۸۰ نام آیکون مشترک @forms
  form_kind: "accident" | "incident_report"; // پیش‌فرض "accident"
  status: "draft" | "active" | "archived";   // پیش‌فرض "draft"
  version: number;                            // پیش‌فرض ۱، در activate افزایش می‌یابد
  schema_version: number;                     // پیش‌فرض ۱
  definition: { schemaVersion?, name?, pages? };
  createdAt, updatedAt;
}
```

روابط: `organization` (تکی، **الزامی**، معکوس `form_definitions`) و `registrer`
(تکی، اختیاری).

دیگر `is_active` وجود ندارد — `status` همان واقعیت را حمل می‌کند و دو منبع حقیقت
برای یک واقعیت، همان چیزی است که یک فرم را هم‌زمان بایگانی و فعال می‌کند.
`incident_type` هم حذف شده و `form_kind` جای آن را گرفته است؛ تعداد فرم‌ها در هر
نوع عمداً نامتقارن است.

دو ایندکس این نامتقارنی را تضمین می‌کنند:

- **ایندکس یکتای جزئی** روی `{ "organization._id" }` با فیلتر `status: "active"`
  تضمین می‌کند هر سازمان حداکثر **یک فرم فعال تصادف** داشته باشد. ثبت تصادف یک
  گردش‌کار است و فرم فعال دوم، «فرم تصادف» را برای همهٔ کلاینت‌ها مبهم می‌کند.
- `{ "organization._id", "form_kind", "status" }` برای فهرست‌های پشت `getForPatrol`
  و بیلدر. فرم‌های `incident_report` **محدودیتی ندارند** — سازمان به اندازهٔ
  گردش‌کارهایش فرم می‌نویسد.

`activate` قاعدهٔ تک‌فرمی بودن را در نرم‌افزار هم اعمال می‌کند تا کاربر به‌جای خطای
کلید تکراری، پیام فارسی دریافت کند.

### form_response

پاسخ‌های یک مأمور به یک نسخه از تعریف.

```ts
{
  form_definition_id: string;   // ObjectId خام — توضیح پایین
  definition_version: number;
  client_report_uuid?: string;  // هماهنگ با accident.client_report_uuid
  answers?: Record<string, unknown>;              // درخت تودرتو، همان‌طور که ارسال شده
  flat_answers?: Array<{ field_key, path?, value?, values? }>;
  errors?: Issue[];   // { path, node_key, message, severity }
  warnings?: Issue[];
  createdAt, updatedAt;
}
```

روابط: `organization` (تکی، الزامی)، `definition` (تکی، اختیاری)، `officer` (تکی،
اختیاری)، `accident` (تکی، اختیاری).

> **`form_definition_id` یک ObjectId خام است، نه رابطه.** گزارش ثبت‌شده باید پس از
> حذف تعریفش هم خوانا بماند — مقاومت یتیم، مطابق `back/AGENTS.md`. رابطهٔ
> `organization` اتصال زندهٔ مالکیت را فراهم می‌کند.

`flat_answers` نمایش تخت‌شدهٔ همان داده است، تا یک گزارش بدون خط لولهٔ اختصاصی برای
هر فرم قابل جست‌وجو و تجمیع باشد.

## `activate` — دروازهٔ پیش‌نویس تا میدان

این تنها جایی است که *معناشناسی* یک تعریف بررسی می‌شود. فرم‌ساز یک ابزار
راحتی است، نه مرجع.

```
۱. رد کردن در صورتی که از قبل فعال باشد
۲. assertOrgInActorScope
۳. validateDefinitionStructure      → کلیدهای یکتا، عملگرهای شناخته‌شده، داشتن مسیر
۴. checkReferenceModels            → هر مدل مرجع موجود است و رکورد دارد
۵. checkBindings                   → هر binding از نوع relation/dto به هدفی واقعی اشاره
                                      می‌کند و روی فیلد reference است
۶. checkIcons                      → هر آیکون در واژگان مشترک ۸۰ نامی هست
۷. بایگانی تعریف فعال قبلی برای همین (سازمان، form_kind) — فقط تصادف
۸. status=active، version+1
```

گام ۵ دلیل آن است که ویجت در زمان انتشار اعتبارسنجی می‌شود نه در زمان ثبت: یک
binding از نوع relation تنها وقتی معتبر است که *مدل هدف واقعاً* آن رابطه را
اعلام کرده باشد (مشتق‌شده از `getSchemas()[target].mainRelations` در Lesan، نه یک
فهرست دستی) و تنها روی فیلد `reference`. مأمور نباید بعد از پر کردن فرم در
کنار جاده متوجه شود که فرم خراب است.

شکست‌ها پیام فارسی می‌دهند:

- «فرم باید حداقل یک صفحه داشته باشد»
- «کلید «x» بیش از یک بار استفاده شده است؛ کلیدها باید یکتا باشند.»
- «عملگر «exec» در شرط نمایش فیلد «x» شناخته نشده است.»
- «شرط الزام فیلد «x» به مسیر فیلد نیاز دارد.»
- «مدل «collision_type» هیچ رکوردی ندارد؛ گزینه‌ای برای نمایش وجود ندارد.»
- «آیکون‌های نامعتبر در فرم: road»
- «فرم فعال قابل ویرایش نیست؛ ابتدا آن را غیرفعال کنید»
- «فرم فعال قابل حذف نیست؛ ابتدا آن را بایگانی کنید»

تعریف ردشده **پیش‌نویس باقی می‌ماند**.

## `getForPatrol` — مسیر زمان اجرا

درخواست:

```jsonc
{ "set": { "formKind": "accident" | "incident_report", "orgId": "…" , "definitionId": "…" },
  "get": { "form": 1, "options": 1, "version": 1 } }
```

ترتیب حل:

۱. **سازمان.** Ghost/Manager باید `orgId` بدهد. بقیه به‌ترتیب از
   `roles[].scopeType === "organization"` ← `unit` ← `unit.organization` ←
   `unit.officers` حل می‌شوند. اگر هیچ‌کدام نبود، خطا می‌دهد:
   «سازمان مأمور یافت نشد؛ ابتدا در واحد گشت عضو شوید».
۲. **تعریف.** `definitionId` صریح، یک پیش‌نویس را برای پیش‌نمایش می‌گیرد (در
   فرم‌ساز استفاده می‌شود). در غیر این صورت تعریف فعال سازمان برای این `form_kind`
   برنده است. اگر سازمان فرم فعال تصادف نداشته باشد، پاسخ `{ form: null }` یک
   پاسخ معتبر است — کلاینت باید به تعریف داخلی خودش برگردد، نه اینکه مأمور را
   متوقف کند.
۳. **گزینه‌ها.** هر مدل `reference` در درخت به
   `{ model: [{ _id, name }] }` تبدیل می‌شود، یک کوئری به ازای هر مدل.
۴. **حذف فهرست مجاز.** `allowedIds` از تعریف بازگشتی حذف می‌شود.

پاسخ:

```jsonc
{
  "form": { "_id", "name", "schema_version", "definition": { … } } | null,
  "options": { "collision_type": [{ "_id", "name" }], … },
  "version": { "version": 2 }
}
```

`{ "form": null }` یعنی سازمان هیچ فرمی برای این نوع رخداد منتشر نکرده — **خطا
نیست**. فراخوان به جریان داخلی برمی‌گردد.

حل گزینه‌ها عمداً سمت سرور است. فهرست گزینهٔ محدودشده را نمی‌توان روی دستگاهی که
ممکن است آفلاین باشد و اصلاً نتواند یک مدل مرجع را پیمایش کند، محاسبه کرد.

## `validate` — ارزیابی شرط‌ها سمت سرور

درخواست:

```jsonc
{ "set": { "_id": "<definitionId>", "answers": { … }, "pageKey": "scene" },
  "get": {} }
```

تابع `validateForm` — **همان تابعی که موبایل آفلاین اجرا می‌کند** — را روی تعریف
ذخیره‌شده اجرا می‌کند. همین، بک‌اند را مرجع می‌کند: کلاینت منسوخ، دست‌کاری‌شده یا
نسخهٔ قدیمی‌تر نمی‌تواند فرمی برخلاف تعریف خودش ثبت کند.

پاسخ:

```jsonc
{
  "errors":   [{ "path": "vehicles[0].type", "node_key": "vehicleType",
                 "message": "نوع وسیله نقلیه الزامی است.", "severity": "error" }],
  "warnings": [{ "path": "vehicles[0].mobility", "node_key": "mobility",
                 "message": "این وسیله به جرثقیل نیاز دارد.", "severity": "warning" }],
  "blockedPages": ["scene"],
  "canSubmit": false,
  "definition_version": 2,
  "schema_version": 1
}
```

`pageKey` گزارش را به یک صفحه محدود می‌کند تا بازخورد هر بخش جداگانه باشد.

## `getReferenceOptions`

```jsonc
{ "set": { "model": "collision_type", "ids": […], "search": "بر", "limit": "50" },
  "get": { "model": 1, "items": 1 } }
```

مقدار `model` باید در `REFERENCE_MODEL_NAMES` باشد. این فهرست سفید وجود دارد تا
این اکشن به ابزاری برای پیمایش مجموعه‌های دلخواه تبدیل نشود. سقف `limit` برابر
۵۰۰ است.

## مجوزدهی ماژول

موتور تحت یک کلید ماژول جدید، **`forms`**، گیت می‌شود.

```
سطح نصب   : models/module_config.ts → { key: "app_modules", modules: [...] }
سطح سازمان: organization.module_flags
نگاشت اکشن: back/src/app_modules/moduleConfig.ts
```

| لایه | رفتار |
| ----- | ----- |
| خاموش در نصب | «این ماژول برای این نصب فعال نیست» — Ghost مستثنی است |
| خاموش در سازمان | «این ماژول برای این سازمان فعال نیست» — Ghost مستثنی است |

اسکیماهای گیت‌شده: `form_definition`، `form_response` (با الگوی کل اسکیما).

> **`forms` باید آخرین عضو `MODULE_KEYS` بماند.** تابع `moduleKeyFor` روی
> **اولین** کلید منطبق در آن آرایه برمی‌گردد، پس در غیر این صورت الگوی کل‌اسکیمای
> `incident_patrol` بر اسکیمای forms سایه می‌اندازد.

پرچم‌های غایب سازمان به «فعال» نرمال می‌شوند، پس سازمان‌های موجود بی‌اثر می‌مانند.

اکشن‌های هسته — `accident.get/gets/add/update/remove/count`، احراز هویت، جغرافیا،
مدل‌های مرجع، فایل‌های عمومی، `operation_log` — **هرگز** گیت نمی‌شوند. مجوزدهی
موتور فرم‌ساز نمی‌تواند ثبت گزارش را بشکند.

## همگام‌سازی اعلان‌ها (declaration)

پس از هر تغییر در مدل یا اعتبارسنج:

```bash
cd back && TYPE_GENERATION=true deno run -A mod.ts   # declarations/selectInp.ts را می‌نویسد
cd .. && cp -v back/declarations/selectInp.ts front/src/types/declarations/
```

موبایل نسخهٔ بک‌اند را مستقیم از طریق `@backend/selectInp` می‌خواند. هرگز اعلان را
دستی ویرایش نکنید.

## شکاف‌های شناخته‌شده در بک‌اند

- **`form_response` هنوز اکشن ثبت ندارد.** مدل وجود دارد و پاسخ‌ها اعتبارسنجی و
  نگاشت می‌شوند، ولی چیزی سند پاسخ را ذخیره نمی‌کند. ارسال همچنان از مسیر
  `accident.add` / `accident.update` با فیلدهای typed نگاشت‌شده انجام می‌شود، و
  همین دلیل است که نمودارها امروز کار می‌کنند.
- **`update` جایگزینی کامل است، نه ادغام جزئی.** این عمدی است — فرم‌ساز کل
  پیش‌نویس را یکجا ذخیره می‌کند، پس گرهی که نویسنده حذف کرده واقعاً ناپدید
  می‌شود.
