# Task: serve the `@2x` sprite index so offline map packs can complete

## Context

`tiles/` is the self-hosted vector tile server (native `pmtiles serve` + `caddy`) for the
LESEN/Nejat patrol app. It serves, on one origin (`http://<host>:8790`):

| Path | Artifact |
| --- | --- |
| `/style.json` | MapLibre style (`build/gen-style.mjs`) |
| `/tiles.json` | TileJSON (`build/gen-tilejson.mjs`) |
| `/tiles/{z}/{x}/{y}.mvt` | vector tiles (pmtiles upstream, 200 or 204) |
| `/glyphs/{fontstack}/{range}.pbf` | Persian glyph ranges (`build/gen-glyphs.mjs`) |
| `/sprites/v4/{light,dark}.{json,png,@2x.json,@2x.png}` | icon sprites (vendored under `tiles/sprites/`) |

`dist/` is **gitignored** and is regenerated by `build/gen-artifacts.sh`, which in its last
step just copies the vendored sprite files: `cp -R sprites/. dist/sprites/`.

The mobile client uses MapLibre React Native 11.5.0. Its offline packs are created with
`OfflineManager.createPack({ mapStyle, bounds, minZoom, maxZoom })`, where `mapStyle` is the
`/style.json` URL. MapLibre resolves the region into **every tile, glyph, and sprite the
style needs**, and a region is only usable offline once `status.isComplete` is true.

## Symptom (reported against the production origin `http://46.245.98.207:8790`)

- Offline map downloads stall one resource short of completion, e.g. **4542 / 4543**.
- MapLibre reports the pack as paused/stalled; the client's "resume" re-requests the same
  dead resource and stalls again — it looks like the button does nothing.
- The downloaded map never renders offline.
- Occasionally a **404** surfaces.

## Root cause (verified 2026-10-18)

Probing the live origin, **every** resource the style references returns 200 **except two**:

```
sprites/v4/light.json     200     sprites/v4/light@2x.json   404   <-- missing
sprites/v4/light.png      200     sprites/v4/light@2x.png    200
sprites/v4/dark.json      200     sprites/v4/dark@2x.json    404   <-- missing
sprites/v4/dark.png       200     sprites/v4/dark@2x.png     200
style.json 200   tiles.json 200   glyphs/* (incl. 1536-1791) 200   tiles/* 200|204
```

On a display with device‑pixel‑ratio ≥ 2, MapLibre requests the **`@2x.json`** sprite index.
That file counts toward the offline region's `requiredResourceCount`. A 404 is never counted
as completed, so `status.isComplete` can never become true and the region freezes at
`requiredResourceCount − 1` (the 4543rd resource is `light@2x.json`). Diagnose with
`MLRNOfflineModule.kt` `makeRegionStatus`: `state = "complete"` iff `status.isComplete`.

The mobile app is **not** at fault; it maps MapLibre's `inactive`+progress to "paused"
correctly. **Do not change the app in this task.**

## Why this is a platform invariant, not a one‑off

For MapLibre **any 404 on a style‑referenced asset silently stalls every offline pack** — the
download runs to 99.98%, the region ends `inactive`, and it never becomes usable offline.
So the server must never 404 a style‑referenced asset. (Out‑of‑coverage tiles returning 204
is fine; that is already correct.)

The two missing files were added by hand in commit `da7304f`, but:

1. nothing generates them, so any future sprite refresh drops them again, and
2. `dist/` is gitignored, so committing `sprites/*@2x.json` does **not** update the running
   origin until `build/gen-artifacts.sh` is re‑run on the host — which is why production
   still 404s.

## Required changes

### 1. Generate the sprite indices (no hand‑edited JSON)

Add `build/gen-sprites.mjs` that, for each flavor (`light`, `dark`), reads the vendored
1× index `sprites/v4/<flavor>.json` and the PNGs, and **writes** `sprites/v4/<flavor>@2x.json`
by mapping every entry to:

```json
{ "x": 2*x, "y": 2*y, "width": 2*width, "height": 2*height, "pixelRatio": 2 }
```

The generator **must fail the build** (non‑zero exit) unless all of these hold for each flavor:

- `sprites/v4/<flavor>@2x.png` dimensions are exactly 2× `sprites/v4/<flavor>.png`
  (currently 256×114 → 512×228).
- The 1× and 2× index name sets are **identical** (currently 53 icons each).
- Every `@2x` entry equals 2× its 1× counterpart with `pixelRatio: 2`.

Wire it into `build/gen-artifacts.sh` so `dist/sprites/` is produced by the generator
(keep copying the vendored PNGs, but generate the `@2x.json` files rather than trusting a
static file). Keep `dist/` a generated artifact.

> Do **not** "fix" this by pointing `@2x.json` at the 1× JSON. The 1× index has
> `pixelRatio: 1` and half coordinates; a ≥2× device would draw icons at the wrong size and
> position. The real doubled index must exist.

### 2. Make `verify.sh` catch this class of bug

`verify.sh` already lists the style's sprite URLs (criterion 3), but only the sprite named in
`style.json` (`light`) and without validating content. Extend it so the harness fails when:

- All four URLs for the referenced sprite return 200 (already), **and**
- The `@2x.json` is internally consistent: same names as the 1× index, every geometry doubled,
  `pixelRatio == 2`, and the `@2x.png` dimensions are 2× the 1× PNG.
- Both `light` **and** `dark` sprite sets are served (both are shipped artifacts; a future
  dark flavor must not silently 404).

Keep the harness deterministic and dependency‑free (node is already available; `jq`/`python3`
are already required).

### 3. Close the deploy gap (README runbook)

Document, in `tiles/README.md` (sections 2 / 10 and the artifact notes), that:

- Every asset `style.json` references must return 200 on the live origin; a 404 stalls all
  offline packs (state the invariant).
- Because `dist/` is gitignored, deploying a sprite/asset change requires re‑running
  `TILES_PUBLIC_ORIGIN=<origin> ./build/gen-artifacts.sh` on the host and restarting
  `./run-local.sh`.
- The deploy gate is running the harness against the live origin:
  `BASE=<origin> ./verify.sh` → `FAIL=0`.

## Acceptance criteria

Run on the host that serves the origin (node via fnm `v22.22.2`, `jq` 1.7.1 on `PATH`):

```bash
cd tiles
TILES_PUBLIC_ORIGIN=http://46.245.98.207:8790 ./build/gen-artifacts.sh
BASE=http://46.245.98.207:8790 ./verify.sh        # must end: FAIL=0
```

Direct checks, all `200`:

```bash
for u in light dark; do
  for f in json png @2x.json @2x.png; do
    printf '%s %s -> ' "$u" "$f"
    curl -s -o /dev/null -w '%{http_code}\n' \
      "http://46.245.98.207:8790/sprites/v4/$u.$f"
  done
done
```

Content check for the generated index (must print `ok` twice):

```bash
cd tiles
node -e '
const fs=require("fs");let ok=0;
for(const n of ["light","dark"]){
  const j1=JSON.parse(fs.readFileSync(`dist/sprites/v4/${n}.json`));
  const j2=JSON.parse(fs.readFileSync(`dist/sprites/v4/${n}@2x.json`));
  const names=k=>Object.keys(k).sort().join();
  const good=names(j1)===names(j2)&&Object.keys(j1).every(k=>{
    const a=j1[k],c=j2[k];
    return c.x===2*a.x&&c.y===2*a.y&&c.width===2*a.width&&c.height===2*a.height&&c.pixelRatio===2;
  });
  console.log(n,good?"ok":"BAD");if(good)ok++;
}
process.exit(ok===2?0:1);
'
```

Device acceptance (mobile, no code change): a national or area pack reaches **100% / complete**,
`completedResourceCount == requiredResourceCount`, and the base map renders with the phone in
airplane mode.

## Constraints

- Follow the existing `tiles/` conventions: shell for orchestration, `build/*.mjs` for
  generation, `dist/` always regenerated (never committed), `verify.sh` as the acceptance
  harness.
- Do not change the style origin handling (`TILES_PUBLIC_ORIGIN` bakes into
  `dist/style.json` / `dist/tiles.json`).
- Do not touch `mobile/`. The client already handles pack status correctly.
- Keep all existing `verify.sh` criteria passing.

## Out of scope

- Mobile app changes.
- HTTPS/domain setup (tracked separately).
- Adding new sprite flavors beyond `light`/`dark`.
